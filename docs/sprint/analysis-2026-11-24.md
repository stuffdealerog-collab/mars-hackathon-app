## PRODUCT & PROMISE

Mercat promises that a small-business owner pastes one Telegram channel link and, in about a minute, "10 AI employees" return a Brand DNA, an audit with real numbers, a strategy, a week of posts in four scripts, about 10 places where customers are and a Reels script. The owner only approves, and the bot publishes to their channel. The pitch sets the price at 7 days free, then 149 000 so'm a month (README.md, PRODUCT.md, docs/README.md, pitch.md). In code, a Studio run fires six separate client calls: /brand, /posts with count=2, /radar, /video, /analyze, and /strategy after the audit. Each one quietly falls back to labelled "namuna" mock data on any error (src/components/studio/api.ts, store.ts:235-262). The strongest real asset is the deterministic brain. It scrapes t.me/s, computes stats and fires rules with no LLM at all; a local /analyze of @safiabakery returned 60 posts, 52.4% reach and concrete problems: only 12% of sale posts show a price and 5% have a CTA. The second real asset is the Telegram bot path: link, then DNA summary, then 2 posts with a "Publish to @channel" button that checks owner and admin rights (onboard.ts:77-99). The promise breaks at the joints. The 7-day plan never feeds the copywriter (Studio writes 2 generic posts from the task text). Web publishing deep-links to a bot payload that nothing handles, and the bot's "open Studio" buttons pass ?brand= that nothing reads. Dizayner and Videograf generate nothing in the UI, and the Team view shows invented "today" activity. Contrary to the assumption, the production LLM works: one /api/uslub/neuro call on uslub-ai.vercel.app came back in "rewrite" mode, which only Claude output can produce. My judgement: the product is useful to an Uzbek SMB owner only as a short Telegram-native loop: "here is what is wrong with your channel this week, here are your next 3 posts in your voice with a picture, tap to publish". Everything else (10 lamps, node canvas, Spektr, radar, autopilot, ledger ids, English/Cyrillic by default) is noise for tomorrow's 2-3 clients. The single most valuable outcome is a ready-to-publish post in the owner's own voice, grounded in their real facts and fixing a measured problem (missing price or CTA), published from Telegram in one tap. The ideal path has 3 steps: (1) paste the link and see 3 plain-language findings with numbers, (2) review 3 posts written from the plan, each with an image in the channel's style, (3) approve and publish through the bot.

## Gargona brain, cloud and service (C:\Users\st3rvoz\Downloads\FABLE GAME\gargona, branch feat/cloud-subscribers @9d845c1): is it usable by Mercat for image/video generation by tomorrow

Gargona has four parts. (1) An Electron desktop studio, v1.2.0, installed at %LOCALAPPDATA%\Programs\Gargona. It has an engine (src/engine), a motion head that renders HTML/GSAP/three.js frame by frame in hidden (offscreen) Electron Chromium windows (src/main/motion-host.ts), and a control server that listens only on this PC with a bearer token (src/main/control-server.ts, POST /rpc). (2) An MCP bridge called "gargona" (src/mcp/server.ts). Claude Desktop or Claude Code launches it over stdio and it drives the running editor. It is connected in this session. (3) The "brain". In the app it is the user's own Claude Code CLI running as a subprocess (src/main/brain.ts). Optionally it is the "cloud brain" (cloud/brain, Anthropic SDK), which runs on the gateway but sends every tool call back to the creator's local Gargona MCP over SSE `relay` events (cloud/brain/src/contract.ts lines 19-21). So the cloud brain can render nothing without a running desktop editor. The flow is: POST a job, the server picks the first configured provider and builds the prompt from one of 5 fixed style presets, the job is stored, then the browser polls (the server calls the provider at most every 4 s, with a 20 min timeout) until it can cancel or read the result. Routes: GET /api/uslub/media (status), POST/GET /api/uslub/media/jobs, POST /api/uslub/media/jobs/cancel and POST /api/uslub/media/captions. /api/uslub/video is a separate route that only asks Claude for a text storyboard (VideoPlan); it renders nothing. Default models: fal Kling 2.6 Pro image-to-video and Nano Banana Pro edit; Higgsfield Seedance 2.5 image-to-video and Marketing Studio Flare (GPT Image 2.5). A job takes exactly one product photo (https or data URL ≤3 MB). There are no multiple reference images, no text-to-image, no video input and no brand or channel style input. Ownership: a job belongs to "tg:<id>" or "anon". Spend has a per-user cap, a shared anonymous cap and an app-wide daily cap, and the check-and-insert runs in one Postgres transaction. Results stay on provider URLs because the `archive` hook is never wired. No Studio component calls the media routes: the Videograf panel shows "Render tez kunda" ("render coming soon") and the Dizayner node only relabels posts. The "3D constellation" is a Blender-built set of 10 orbs plus a lime core in public/media/3d. It is decoration and pitch-film material, used in code only as the demo provider's fake output. Gargona cannot yet render for Mercat over an API. Its cloud pipeline only cuts or transcodes uploaded assets (draft540/final1080/transcribe), and three.js clay/blockout renders run only inside the desktop app.

## GARGONA MOTION / 3D ENGINE

Gargona's motion head is the desktop Electron app, not a server library. src/main/motion-host.ts loads each HTML/GSAP/three.js composition into an offscreen Electron BrowserWindow with assets/motion/runtime.js injected first. runtime.js replaces the page's clocks (requestAnimationFrame, performance.now, Date, timers, CSS/Web Animations, GSAP, anime, Lottie, video) with a virtual clock. The host then steps frames with window.__gargonaSeek(t), proves each paint with an 8-cell seek marker drawn below the frame, takes it with capturePage(), and pipes raw BGRA into FFmpeg as a ProRes 4444 (alpha) or ProRes 422 cache file. motion.export (src/engine/studio.ts:1630) re-encodes that cache to MP4 (libx264, CRF 17), WebM, GIF or PNG, and it throws "Motion export needs the Gargona app running" without the desktop host. There is no 3D editor UI: 3D means three.js written into a composition (template assets/motion/templates/three-orbit.html; MCP instructions say "previz, blockouts... you build yourself with three.js"). Blender and Tripo are external MCP heads. The only blockout-plus-passes scene (depth, normals, object ids) is a measurement page, infra/measure/pages/three.html. Storyboard and assemble are desktop-project commands (studio.ts:1016-1135), not a service. Gargona's cloud gateway does not render motion: the pipeline answers motion.* with cloud_unsupported (gateway/src/pipeline/executor.ts:14,257), and docs/online/e13.2.md row 6 names "Playwright with the same runtime.js" as the fallback. I built that fallback in the scratchpad and it works. A param-driven clay blockout (cyclorama, pedestal, lathe or rounded-box product, key/rim/fill lights with soft shadows, push-in/orbit/crane/reveal camera) rendered through Gargona's own runtime.js in Playwright's headless Chromium over CDP into H.264 MP4. A 6 s 1080x1920 clip took 14.8 s on the RTX 5080 and 25.5 s on SwiftShader pinned to 2 logical CPUs. The video-model side is strongest for keyframes: Gargona's registry has image-to-video models that also take an end frame (Kling 3.0 Pro, MiniMax H3, Seedance 2.5), but no verified video-to-video restyle. The quickest path for tomorrow is a clay preview in the browser, then its first/last frames, a fal image edit and fal image-to-video through Mercat's existing media pipeline.
